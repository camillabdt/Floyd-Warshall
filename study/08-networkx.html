NetworkX e complexidade

A biblioteca não resolve o problema por nós. Ela desenha o grafo, calcula posições e fornece um segundo algoritmo para conferir as respostas.

Como responder se perguntarem

Usar biblioteca para desenhar e para conferir é diferente de usar biblioteca para resolver. O algoritmo pedido está implementado no projeto, em floyd_warshall_solver.py, e o baseline existe justamente para provar que ele está certo.

Por que o custo é n ao cubo

São três laços aninhados, cada um percorrendo os n vértices. O corpo do laço mais interno faz uma soma e uma comparação, que custam o mesmo independentemente do tamanho do grafo. Logo, o número de comparações é exatamente n × n × n.

Sem JavaScript: 10 vértices geram 1.000 comparações; 20 geram 8.000; 40 geram 64.000; 80 geram 512.000.

Dobrar o número de vértices multiplica o trabalho por oito, porque 2 elevado a 3 é 8. A memória cresce com n ao quadrado, que são as duas matrizes guardadas.

Por que o problema está na classe P

A classe P reúne os problemas que uma máquina determinística resolve em tempo limitado por um polinômio no tamanho da entrada. O Floyd-Warshall termina em um número de passos proporcional a n ao cubo, que é um polinômio, para qualquer entrada válida. Isso basta para colocar o problema de caminhos mínimos entre todos os pares na classe P.

Medir em vez de supor

O projeto traz um experimento em benchmark, no mesmo arquivo da comparação. Ele monta grafos completos determinísticos de tamanhos crescentes, roda o algoritmo algumas vezes e guarda a mediana dos tempos.

Duas decisões do experimento valem explicar:

  • Aquecimento. A primeira execução é descartada, porque ela paga custos que não se repetem, como a alocação inicial de memória.
  • Mediana, não média. Se o sistema operacional interromper uma das medições, a média sobe; a mediana ignora esse caso isolado.

A coluna ms_per_n3 divide o tempo medido por n ao cubo. Se a teoria descreve bem a prática, essa coluna fica aproximadamente constante conforme n cresce. É essa a evidência que sustenta a afirmação de complexidade, melhor do que só repetir a fórmula.

Confira o entendimento

Para 100 vértices, quantas comparações o algoritmo faz? E para 200?

1.000.000 para 100 vértices e 8.000.000 para 200. O tamanho dobrou, o trabalho ficou oito vezes maior.

Se o grafo tem poucas arestas, o algoritmo fica mais rápido?

Os três laços percorrem vértices, não arestas, então o número de repetições não muda. Os dois continue economizam contas em grafos esparsos, mas a complexidade no pior caso continua sendo n ao cubo. Para grafos muito esparsos, rodar Dijkstra a partir de cada vértice costuma sair mais barato, desde que não haja peso negativo.
